## 🔴 HIGH (1)

### HIGH-1: Przejściowy błąd verify w P24 kończy się HTTP 200 do P24 — notyfikacja nigdy nie zostanie ponowiona, opłacone zamówienie wisi jako pending

- **Plik**: `app/_lib/p24.ts:118` · **Wymiar**: Płatności P24/zamówienia
- **Opis**: verifyTransaction zwraca false zarówno dla definitywnej odmowy weryfikacji, jak i dla KAŻDEGO przejściowego błędu (5xx z P24, rate-limit, niepoprawne body przy res.ok=false). Caller w app/api/p24/status/route.ts:104-106 traktuje false jako stan ostateczny i odpowiada `NextResponse.json({ received: true })` ze statusem 200 — a P24 ponawia notyfikację tylko przy odpowiedzi innej niż 200. Skutek: jedna chwilowa awaria po stronie P24 podczas verify i zamówienie na zawsze zostaje pending, transakcja nie zostaje zweryfikowana po stronie P24 (bez wywołania verify środki nie są rozliczane dla sprzedawcy), a klient dostał komunikat o przetwarzaniu płatności. Kontrast: gdy fetch rzuci wyjątkiem (błąd sieci), wyjątek propaguje z route → 500 → P24 ponowi; ścieżka res.ok=false zachowuje się gorzej niż ścieżka twardego wyjątku.
- **Dowód**: `p24.ts:118 'if (!res.ok) return false;' … route.ts:104-106 'if (!verified) { console.error('P24 status: verify nieudany dla ${orderId} — zostaje pending'); return NextResponse.json({ received: true }); }'`
- **Jak naprawić**: Rozróżnij wynik: verify=declined (definitywne, np. 400/status!=success) vs verify=transient-error (5xx/sieć). Dla transient zwracaj z route status 500, żeby P24 ponowiło notyfikację; ewentualnie rzucaj wyjątek z verifyTransaction dla res.status>=500.

### MEDIUM-1: Brak guardu finalTotal > 0 — kod rabatowy 100% prowadzi do rejestracji P24 z amount=0 i 500 po utworzeniu zamówienia

- **Plik**: `app/api/checkout/route.ts:219` · **Wymiar**: API routes
- **Opis**: validatePromoCode pozwala na rabat równy wartości koszyka (percent 100 lub fixed >= total; promo.ts:95 przycina discount do cartTotal). P24 odrzuca rejestrację (registerTransaction rzuca przy !res.ok, p24.ts:81-83), klient dostaje 500, a w DB zostaje osierocone pending-zamówienie. Każdy checkout z takim kodem deterministycznie kończy się 500.
- **Dowód**: `const finalTotal = toCharge(Math.max(0, total - promoDiscount)); ... const token = await registerTransaction(buildP24RegisterParams({ orderId: order.id, finalTotal, ... })); // amount: Math.round(args.finalTotal * 100)`
- **Jak naprawić**: Przed createOrder odrzucić (400) lub obsłużyć osobną ścieżką zamówienia z finalTotal <= 0 (np. minimalna kwota 1 gr / darmowe zamówienie bez P24).

### MEDIUM-3: Konwersja EUR per pozycja (Math.ceil) — suma cen pozycji może przekroczyć pobrany total zamówienia

- **Plik**: `app/api/checkout/route.ts:230` · **Wymiar**: API routes
- **Opis**: convertToEur robi Math.ceil (money.ts:8). toCharge stosowane jest osobno do każdej ceny jednostkowej pozycji i osobno do sumy, a sum(ceil(x_i)) >= ceil(sum(x_i)). Np. dwie pozycje po 430,60 zł przy kursie 0.2325: cena pozycji ceil(100.11) = 101 EUR każda (razem 202), ale total = ceil(200.22) = 201 EUR. Klient płaci 201, a rekordy order_items sumują się do 202 — niespójność w historii zamówień, mailach i panelu admina (rozjazd rośnie z liczbą pozycji).
- **Dowód**: `items: orderItems.map((it) => ({ ...it, price: toCharge(it.price) })), total: finalTotal, // finalTotal = toCharge(Math.max(0, total - promoDiscount))`
- **Jak naprawić**: Konwertować raz na poziomie sumy, a ceny pozycji przeliczać proporcjonalnie (lub zapisywać pozycje w PLN + fx_rate, licząc EUR tylko dla total).

### LOW-33: Karta pozycji koszyka nie stackuje się na mobile — stepper ilości (114px) nie mieści się w kolumnie ~102px przy 320px
